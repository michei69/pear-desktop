# Architecture

## Process model

| Surface          | Entry point                         | Role                                                                 |
| ---------------- | ----------------------------------- | -------------------------------------------------------------------- |
| Main process     | `src/index.ts`                      | Window/tray/menu/protocol, config store, main-process plugins, themes |
| Preload          | `src/preload.ts`                    | Loads i18n and preload plugins, exposes the bridge, injects the renderer |
| Renderer         | `src/renderer.ts`                   | Page-world boot in the YouTube Music window; renderer plugins, themes, player API |
| Settings window  | `src/settings-window.ts` + `?settings=1` | Standalone settings UI loading the same renderer bundle           |

## Boot sequence

Main process (`src/index.ts`):

1. Single-instance lock, custom `youtubemusic://` protocol registration, GPU and feature switches, proxy selection, About-panel metadata.
2. `app.whenReady`: permission handlers and spellchecker disabled, stale code-cache cleanup, app language default, `loadI18n`, then `setupThemes()` (seed/migrate/read theme folders, consent for the selected theme). Flag metadata loads afterwards without blocking the window.
3. `createMainWindow()`: builds the `BrowserWindow`, registers the per-plugin config IPC and config watcher (`initHook`), then `loadAllMainPlugins(win)`.
4. After the window exists: memory reporting, application menu, tray, shortcut icons, protocol handler, updater, and the second-instance handler.

Preload (`src/preload.ts`):

1. `loadI18n(active language)` - English plus the active language.
2. `loadAllPreloadPlugins()` after i18n resolves.
3. Expose the bridge and register `plugin:enable` / `plugin:unload` forwarding.
4. If performance mode is on, install the animation throttle into the page before the app's own renderer runs.
5. Synchronously ask main for the renderer script (`get-renderer-script`) and execute it in the page world, prefixing the bundle with the loaded i18n resources as `globalThis.__PEAR_I18N_RESOURCES__`. In dev, this instead injects Vite's client and `renderer.ts`.

Renderer (`src/renderer.ts`):

1. If `?settings=1`, boot the standalone settings UI and stop.
2. Otherwise start `initObserver()`: wait for DOM-ready, look for `#movie_player`, call `setupSongInfo(playerApi)` when it appears, and arm a throttled `MutationObserver` while it is missing. The chained `preload()` then loads i18n from the injected resources and `main()` starts the page-side services.
3. `main()` sets up share-link rewriting, the context-menu customizer, loads all renderer plugins, initializes themes, subscribes to plugin enable/unload and `config-changed`, and ends with a one-shot `listenForApiLoad()`.
4. `onApiLoaded()` runs once the player API exists *and* renderer plugins are loaded: video/CORS/audio-graph setup, `onPlayerApiReady` for every loaded renderer plugin, and the `peard:player-api-loaded` signal to main. The song-info listeners themselves are armed by `setupSongInfo` from the observer step.

## Build

The build is driven by `electron.vite.config.mts` and produces three bundles
under `dist/`:

- `dist/main/index.js` - the main process bundle.
- `dist/preload/preload.cjs` - the preload bundle (CommonJS, for the sandboxed preload context).
- `dist/renderer/` - an IIFE bundle injected into the page. Dynamic imports stay in the single file (`codeSplitting: false`) because the preload injects it as one script.

Two virtual modules connect source to build:

- `virtual:plugins` - generated by `vite-plugins/plugin-importer.mts`. It exposes `allPlugins` and a per-target map (`mainPlugins` / `preloadPlugins` / `rendererPlugins`), the renderer-only `rendererPlugin` and `rendererPluginMeta`, and `supportsPlatform`. The generated module imports each plugin lazily (main) or statically (preload/renderer), and filters by platform. `vite-plugins/plugin-loader.mts` also synthesizes a `pluginStub` export that contains the plugin definition with the other process halves stripped, so the main bundle does not pull in renderer code (and vice versa).
- `virtual:i18n` - generated by `vite-plugins/i18n-importer.mts`. It exports the language codes, the per-language metadata, and a loader per locale. In the renderer it only exposes the resources preload injected; the renderer bundle carries no translations.

Aliases are `@` → `src/` and `@assets` → `assets/`. `node-smtc` is kept external because it is a Windows-only optional dependency. `PEAR_CHANNEL` and `PEAR_COMMIT` are baked in as `__PEAR_CHANNEL__` / `__PEAR_COMMIT__` for the About window and updater (`src/app-info.ts`).

Useful commands: `pnpm dev` (build + watch), `pnpm build`, `pnpm start`
(preview), `pnpm clean`, `pnpm check`, `pnpm test`.

## Plugin loading at runtime

Plugin discovery, lifecycle and the per-process contexts are covered in
[Plugins](./plugins/index.md). The parts that matter at the architecture level:

- `src/loader/main.ts`, `src/loader/preload.ts` and `src/loader/renderer.ts` each own a `loadedPluginMap`, create a fresh context per lifecycle call, and keep a per-plugin listener registry so `off` removes exactly the listener a plugin registered.
- Enabling/disabling a plugin at runtime is signalled from main over `plugin:enable` / `plugin:unload` to preload and the renderer, and `ipcMain.emit(...)` for main-process plugins. The main-process config watcher (`initHook`) drives this when `plugins.<id>.enabled` changes.
- The renderer reads static metadata from the generated `rendererPluginMeta` to decide which plugins to start without resolving definitions that are statically known to be disabled or platform-mismatched; if a field could not be read statically, it falls back to importing the definition. The main build uses deferred dynamic imports, so a main-process plugin module evaluates only when loaded; the renderer and preload builds import every plugin entry statically, so their top-level code is part of the bundle and evaluates with it. Keep plugin top-level code side-effect-free either way.
- `restartNeeded` does not unload/reload anything by itself: main shows the restart dialog (or batches it for the settings window) and the user restarts.
- Performance mode can skip the renderer half of a fixed list of visual plugins (`src/providers/performance-mode.ts`) without touching their config.

## Configuration

Configuration is an `electron-store` (the `conf` package) instance persisted to `<userData>/config.json` (`src/config/store.ts`). Shape and defaults live in `src/config/defaults.ts`; the store is typed from that object.

- `config.get(key)` reads a dotted path (`plugins.synced-lyrics.enabled`).
- `config.set` / `setPartial` / `patch` write; `setPartial` deep-merges into the existing object using `deepmerge-ts` with **arrays replaced, not concatenated** (`mergeArrays: false` in `src/config/index.ts`). Plugin config is merged over the plugin's own `config` default by the loaders with the default `deepmerge-ts` behaviour, where arrays *do* concatenate - a default array can therefore be prepended to the stored one (see the comment in `src/plugins/synced-lyrics/index.ts`). Prefer omitting default arrays when the value is user-editable.
- `config.watch` observes the whole store; main uses it to start/stop plugins, show restart dialogs and broadcast `config-changed`.
- Migrations are keyed by version in `src/config/store.ts` (for example `'>=3.12.3'`). They run once, move/rename/delete stored keys, and never touch keys the user did not have.
- Options read only at startup are marked `restartNeeded` in the settings schema; the menu sets `restartOnConfigChanges` to restart on any menu write when the user opted in.
- Side effects of option writes go through `src/providers/option-effects.ts` so the native menu and the in-app settings behave the same.
- The renderer sees only the allowlisted `mainConfig` keys; plugin code that needs a new option in the page must add it to `rendererConfigKeys` in `src/preload.ts`.

## I18n

Translations are plain JSON resources in `src/i18n/resources/<code>.json`. Each resource starts with a `language` metadata block (`code`, `name`, `local-name`). `i18next` is initialized in `src/i18n/index.ts` with English as the fallback; only the active language plus English are loaded at startup, and other languages can be loaded on demand when the user switches (`loadLanguage`).

The renderer has no resource loaders of its own: preload serializes the loaded resources into the injected script (`getLoadedResources`), and the renderer initializes i18next from `globalThis.__PEAR_I18N_RESOURCES__`. The standalone settings window does the same through the same preload.

Conventions for keys, mandatory English entries and translations are in
[Conventions](./conventions.md#user-facing-text-and-translations).

## Themes

The theme engine is main-process owned (`src/themes/main.ts` + `load.ts`) and
renderer-applied (`src/themes/renderer.ts`). Main reads theme folders from
`<userData>/themes`, validates each `theme.json`, concatenates the declared CSS,
hashes the declared JS, and gates JS behind user consent. The renderer requests
the state over `peard:get-themes`, injects the selected theme's CSS then the
palette as `--pear-theme-*` custom properties, and runs the theme script's
`mount`/`unmount` hooks. Changes from main are pushed as `peard:themes-changed`.
Details: [Themes](./themes/index.md) and [Writing a theme](./themes/authoring.md).

## Player and song-info pipeline

The player API is YouTube Music's own player object reachable as `#movie_player` in the page. The renderer finds it with a `MutationObserver`, waits until it exists and until renderer plugins are loaded, then calls every renderer plugin's `onPlayerApiReady(api, context)` with the `MusicPlayer` object (`src/types/music-player.ts`). The integration guide is [Player API](./plugins/player-api.md).

Song information flows from the page to the rest of the app:

1. `src/providers/song-info-front.ts` listens to the player (`videodatachange`, `onVideoProgress`, ...) and to the media element, reduces the player response with `toSongInfoSource` (`src/providers/song-info-data.ts`), and sends that projection plus playback events to main over `peard:*` IPC.
2. Main's `src/providers/song-info.ts` calls `buildSongInfo` on the projection, applies scrobble/artist options, caches album art, and emits `peard:update-song-info` to the renderer plus a callback to main-process consumers.
3. Consumers subscribe through `registerCallback` / `SongInfoEvent` (`VideoSrcChanged`, `PlayOrPaused`, `TimeChanged`) or through their own IPC listeners: tray, taskbar/SMTC, MPRIS, notifications, Discord, scrobbler, the API server, and the lyrics plugins.

Event/setup channels use `SONG_INFO_SETUP_CHANNEL` (`peard:setup-song-info-listeners`) with `SongInfoEventFlag` bits, so a consumer asks the renderer to arm only the listeners it needs.

## Settings UI

`settings-ui` is an essential plugin (`src/plugins/settings-ui/`) that renders the in-app settings modal, the standalone settings window, and the sidebar entry that opens them. It is schema-driven:

- App options are described in `src/plugins/settings-ui/schema/app-settings.ts`.
- Plugin options are described by each plugin's `settings` field (`src/types/settings.ts`) and rendered by the same field components.
- Custom field types resolve `"<pluginId>.<componentName>"` through the plugin's renderer `components` map.

Writes go through the `ytmd-sui:*` channels in the plugin backend, which apply the same config helpers and option effects as the native menu. Restart requirements are batched per modal session and shown when the session closes (`ytmd-sui:restart-session-open` / `-close`).

## API server

`api-server` (`src/plugins/api-server/`) is an optional local server built on Hono + `@hono/zod-openapi`, with WebSocket support (`ws`), an MCP endpoint, and v1/v2 route groups. Its state is fed by the same song-info events as the rest of the app; the backend subscribes to `peard:*` events and rebroadcasts state to HTTP/WS clients. It binds to `127.0.0.1:26538` by default, requires an auth strategy unless configured otherwise, and its OpenAPI schema is the documentation source for the HTTP surface. Treat its generated docs as authoritative for endpoint details; this page only records where it lives.

## Performance mode

`options.performanceMode` is an app-level option with four independent parts (`src/providers/performance-mode.ts`): feature-flag overrides, a CSS pass that disables animations/transitions/backdrop filters, an injected Web Animations throttle, and skipping the renderer half of `ambient-mode`, `blur-nav-bar` and `visualizer`. `PEAR_PERF_DISABLE=flags,css,...` turns individual parts off for bisecting. User feature-flag overrides win over the mode's defaults.
